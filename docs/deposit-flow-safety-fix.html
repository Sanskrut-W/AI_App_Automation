Deposit-Flow Safety Fix

Platform: AI-powered mobile testing pipeline Trigger: automation typed into a real-money screen with no authorizing test case Status: fixed & verified live; two follow-on issues open

During a routine run, the automation navigated off-script into Betway ZA's Deposit Funds screen and typed a cached password into its Voucher Pin field — with no test case that authorized touching a real-money flow. This document covers what caused it, the guardrail that now blocks it categorically, and the follow-on hardening that came out of chasing it down.

01 What happened

A step failed to find its target element. Two independent fallback paths in the execution engine each tried to recover on their own — and each was willing to act on whatever it found, without checking where it had landed first.

Screen reached
Deposit Funds → Betway Bucks Voucher

Voucher Pin
Value typed
1234 5678 90
Source of that value
cached test-account password (config/test-accounts.json)

The typed value was an exact match for the test account's password — proof this wasn't a coincidence. A locator-healing fallback, primed to re-enter the login password, fired on the wrong screen and typed it somewhere it was never meant to go. The Redeem button was disabled and nothing was ever submitted, but the intent of the code path was clearly "type the password," aimed at the wrong field.

Two independent gaps, same category of mistake

Both live in TestStepExecutor and LocatorHealingEngine — the two places a failed step tries to recover before it's reported as failed.

  • Overlay dismissal acted first, verified never. tryDismissOverlay() scans the whole current screen for anything that looks like a close/skip/dismiss button, taps the first match, then just retries the original step's same locator. Because header elements like toolbarLogin persist on almost every screen, that retry can pass even while the dismiss-tap quietly navigated somewhere unintended — the check has no way to notice.
  • Coordinate self-heal trusted a stale cache. selfHealViaCoordinates() returned an element's own cached pixel coordinates straight from the repository, with zero comparison against the screen actually on-device right now.

02 The fix: a hard refusal gate

Rather than patch each fallback's logic individually, both now share one categorical rule, checked before any tap or keystroke — not after: 

// src/shared/text/isSensitiveFinancialElement.ts
const SENSITIVE_FINANCIAL_PATTERN =
  /deposit|withdraw|voucher|redeem|top[\s-]?up|card\s*number|cvv|payment/i;

// matched against text, contentDescription, resourceId, and accessibilityId
// of every element on the current screen

If anything on the current screen matches, every recovery strategy refuses outright — self-heal, fingerprint match, and the AI fallback alike — and the step fails safely instead of guessing.

Where it's wired in

LocatorHealingEngine.heal() src/application/use-cases/locator-healing/LocatorHealingEngine.ts

Now parses the current screen's XML before trying any strategy — including the cheap coordinate self-heal that caused the incident. A match refuses coordinate self-heal, fingerprint matching, and the AI fallback in one place.

TestStepExecutor.tryDismissOverlay() src/application/use-cases/test-execution/TestStepExecutor.ts

After the dismiss-tap, re-captures the screen and checks it before ever retrying the original step. On a match, it backs out — tapping the screen's own close control if one exists, otherwise the hardware back button — and fails the step instead of retrying against the wrong screen.

Live-proven, not just unit-tested

Both gates have since fired for real against the live app — refusing to heal, and backing out of a dismiss-tap that landed on Deposit Funds — every time, across every verification run since. See §5.

03 Follow-on hardening

Chasing the incident down surfaced four smaller, related problems. Each is now fixed.

Deterministic test-case ordering changed

core/entities/TestCase.ts · infrastructure/persistence/file-system/FileTestCaseRepository.ts

Execution order used to be whatever the OS's directory listing happened to return — undefined behavior that nothing guaranteed. A test case now carries an optional sequence number; the repository sorts by it (falling back to the old order for anything unsequenced), so a suite's run order is an explicit decision instead of an accident of the filesystem.

Screenshot on every step, not just failures changed

test-execution/TestStepExecutor.ts

The HTML report already had a slot for a per-step screenshot — it just only ever got filled in on failure. Every step now captures one, pass or fail, giving each test case in the report a Playwright-style visual trail instead of only visual evidence of what went wrong.

A raw two-point swipe, alongside the generic scroll new

ActionType.SWIPE · AndroidAppiumDriver.swipe() · IInteractionDriver.swipe()

Found live: Appium's generic mobile: scrollGesture silently did nothing inside a nested navigation-drawer list — confirmed by diffing the screen's XML before and after, byte-for-byte identical. mobile: dragGesture between two explicit coordinates moved the same list correctly. Added as a new step type rather than changing scroll's existing behavior everywhere it's already relied on.

Logout runs automatically after every test case new

TestAccount.logoutSteps · TestExecutionEngine · config/test-accounts.json

Restarting the app doesn't log a session out — the token lives on disk, not in memory, so a fresh process just reads it back. A test account can now carry a logoutSteps recipe; the execution engine runs it after every test case, not just ones that are expected to log in. Its own first step is a "still logged in?" check, so it's a safe no-op on any test case that never logged in — that guard is what makes running it unconditionally, after every single test case, safe. It never counts toward a test case's own pass/fail result.

05 Open issues

Two problems remain, both already understood, neither touched by this fix on purpose:

  • Run-to-run variance in when the drift happens Which test case hits a promotional screen shifts between runs — most likely the app's own rotating promo content, not the harness. The safety gate's job is to make every occurrence safe, not to prevent the app from showing a promo in the first place; it has done that in every run so far.
  • A left-open drawer leaks into the next test case The hamburger-menu test case ends with the nav drawer intentionally left open (that's what it's testing). The next test case in the run inherits that open drawer, which can surface an "Exit Betway?" confirmation dialog that then fails its first step. This is a UI-navigation leak, distinct from the session leak that logout teardown already solves — not yet addressed.
