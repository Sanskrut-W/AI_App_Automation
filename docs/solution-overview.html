Solution Overview

AI-Powered Autonomous Mobile Testing Platform

Point it at an APK once. It walks the app, builds real executable test cases from what it finds, and everything after that runs again — daily, weekly, on demand — without touching an APK, a crawler, or the AI budget a second time.

Stack: TypeScript / Node.js · Appium 2 + UiAutomator2 · Gemini Architecture: Clean Architecture (core → application → infrastructure) Verified against: Betway ZA (com.betwayafrica.za), real device/emulator

--crawl-only stops a full run after generation, before it auto-executes anything — useful for building up the stored suite (or importing a manual one) without spending a device session on a run you're not ready to report on yet.

02 Autonomous crawling

application/use-cases/crawler/ScreenCrawler.ts

Depth-first traversal of the installed app: capture the current screen (screenshot + XML dump + every element on it), tap each clickable candidate, capture what that reveals, and recurse — bounded by --max-depth (default 20) and --max-screens (default 100) as a safety net against infinite loops.

  • Recognizes screens it's already seen. A structural hash of each screen (not pixels — element structure) means a second crawl of the same app only does new work instead of rebuilding everything from scratch.
  • Knows what not to tap. Purpose-built text matchers (isCloseButtonElement, isDangerousActionElement, isAuthElement, isLoginTriggerElement, isSignUpTriggerElement) steer it around logout/exit-confirmation buttons and toward the screens worth exploring — login and sign-up entry points specifically, so those flows get discovered without wandering the rest of the app randomly.
  • Recovers from its own overlay-dismissal. A safety net against a chained popup (close one promo, another opens behind it) caps how many times it will keep dismissing before giving up on that branch.

Output: every screen and element persisted to that app's repositories, plus a navigation graph (which element, on which screen, leads to which other screen) that later stages read.

03 Test generation — four modules

Each module owns its own folder and runs in its own isolated Appium session — a real login in one module never contaminates what another module assumes is on screen.

hamburger-menu deterministic

Walks the navigation graph the crawler built and turns "element X on screen Y opens screen Z" into verify-then-click test steps — no AI, no invented data, just what was actually observed.

login deterministic

Generated only when both --login-mobile and --login-password are given together. Builds verify → click → type → verify → click steps against the real login form the crawler found.

sign-up deterministic

Covers the full registration/KYC form (ID type, date of birth, source of funds, language, terms) with freshly-generated random details per field — sign-up is the one flow where any plausible data is correct, so nothing needs to be real or cached.

manual AI-assisted

ExcelManualTestCaseReader → StepInterpreter (Gemini) → ManualTestCaseGenerator

For the business logic no crawler can infer on its own. Takes a plainly-written Excel sheet ("Enter mobile number (on which account exists)" → "user must be able to enter mobile number") and resolves each free-text step against the elements the crawl already captured. A step that doesn't apply to the native app at all (a leftover "enter the URL…" row from a web test suite) is detected and skipped rather than force-matched to the wrong thing. Imported via --import-test-cases — fully offline, no device, reusing only already-crawled data.

The one generator with no deterministic fallback

Free-text step interpretation is impossible without a language model — there's no graph edge to follow. Every other Gemini-backed piece in this platform degrades gracefully without an API key; this is the one exception, and it fails clearly (not silently) if Gemini isn't configured.

04 Locator healing

application/use-cases/locator-healing/LocatorHealingEngine.ts

Apps change. A resource-id renames, a layout shifts, a button moves. When a stored locator stops resolving, three tiers are tried in order — each one only reached if the one before it can't help — before AI is ever asked anything.

Any successful heal updates the stored locator, so the next run starts from the fixed version — healing compounds instead of repeating.

05 Execution & safety

test-execution/TestExecutionEngine.ts · TestStepExecutor.ts

Each stored test case runs step by step against a real Appium session. A failed step doesn't abort the run — it tries to recover, in order: dismiss a recognized overlay and retry, or heal the locator and retry — and only reports FAILED once both have been tried.

Hardened after a live incident

Both recovery paths used to act first and verify never — a dismiss-tap or a cached-coordinate heal could land on the wrong screen with nothing checking where it ended up. Both now refuse outright, before acting, if the current screen matches a real-money pattern (deposit / withdraw / voucher / redeem / payment). Proven live: it has refused and backed out safely every time this has come up since, across every run.

  • Deterministic ordering. A test case can carry an explicit sequencenumber so a suite's run order is a decision, not whatever the filesystem happened to return.
  • A screenshot for every step, pass or fail — not just failures — so the report shows a full visual trail per test case.
  • A raw two-point swipe alongside the generic scroll action, for scrollable content (nested drawer lists) the generic gesture can't reliably reach.
  • Automatic session teardown. A configured account can carry a logoutSteps recipe that runs after every test case — gated by its own "still logged in?" check, so it's a safe no-op on any test case that never logged in. No test case inherits a session left behind by whichever one ran before it.

06 Reporting

infrastructure/reporting/ReportGenerator.ts · HtmlReportRenderer.ts

Every run produces both a JSON report (machine-readable, for anything that wants to consume results programmatically) and a self-contained HTML report: per-test-case pass/fail, per-step screenshots and timings, and the app's navigation graph rendered as a chip-and-edge diagram — one file, no server required to view it.

07 Per-app isolation

shared/paths/AppPaths.ts

Every app's screens, elements, test cases, navigation graph, screenshots, and reports live under artifacts/apps/<packageName>/ — physically separate folders, not a shared table filtered by package name. This exists because of a real bug: executing a freshly-crawled app once ran a leftover test case from an unrelated app, because everything shared one flat repository. Isolation makes that structurally impossible rather than patched around.

It's also what makes --execute-only meaningful: a package name is enough to find and run that app's entire stored suite, with nothing else needed. "Generate once, execute daily" is a direct consequence of this layout, not a separate feature bolted on top of it.

08 Where AI is (and isn't) used

The deterministic-first shape of this platform is a cost decision as much as a reliability one — Gemini is asked for exactly three things, all narrow, all as a fallback.

Call siteAsked to doReached how often
Locator healing (tier 3)Pick a candidate index for a broken locatorOnly when deterministic fingerprint matching's best score is below 0.6
Manual step interpretationMap one free-text Excel row to an action + candidate elementOnce per row, during import — the only unavoidable one
Screen analysis (AiScreenAnalyzer)Structured read of a screen's screenshot + XMLBuilt and available; not called by the current pipeline

Three of the four generation modules (hamburger-menu, login, sign-up) invent nothing and ask Gemini nothing — they're built entirely from the crawler's own structural data. Even where Gemini is used, it's kept to classification/matching, never to inventing real values: manual's mobile-number and password fields are resolved in code from config/test-accounts.json, and sign-up's random details come from a plain random generator, not a model.

09 CLI reference

Full run — crawl, generate, execute the hamburger-menu module, report
npm start -- --apk <path> (--device <serial> | --avd <name>) [options]
--max-screens <n>Cap distinct screens explored (default 100)
--max-depth <n>Cap DFS recursion depth (default 20)
--login-mobile / --login-passwordBoth required together to also generate the login module
--crawl-onlyStop after generation — skip auto-executing hamburger-menu
Execute-only — re-run one module's stored suite, nothing else
npm start -- --execute-only --package <name> --module <name> (--device | --avd)

No APK, no crawl, no AI call — module is one of hamburger-menu, login, sign-up, manual.

Import — turn a manual Excel sheet into a real, executable suite
npm start -- --import-test-cases --package <name> --excel-file <path>

Offline — reuses elements/screenshots a prior crawl already captured. Run the result later with --execute-only --module manual.

List apps with a stored suite
npm start -- --list-apps

11 Open questions

  • Run-to-run variance in the app's own promotional content Which test case encounters a promo screen shifts between runs. The safety gate makes every occurrence safe; it doesn't (and isn't meant to) stop the app from showing one.
  • A test case can leave UI state open for the next one Logout teardown solves session leakage between test cases; a left-open drawer or dialog is a different kind of leak, not yet addressed the same way.
  • User-authored test flow/logic, beyond Excel free text Raised early on and deferred: whether there's room for defining custom test logic directly, rather than everything being crawl-derived or Excel-interpreted. Still open, never designed.
