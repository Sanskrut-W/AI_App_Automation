Solution & Architecture Reference

AI-Powered Autonomous Mobile Testing Platform

A TypeScript platform that crawls a real Android app, generates executable test cases from what it finds, runs them against physical devices, and repairs its own locators when the UI moves underneath it. Built and proven against a production betting app whose entire content area is a WebView.

01 What it does

Four operating modes, one codebase. Each is a distinct entry point through the same CLI, sharing the same domain model and the same device drivers.

ModeInvocationWhat happens
Full run --apk <path> --device <serial> Installs the APK, crawls the app depth-first, persists every screen and element, generates test cases, then executes the hamburger-menu suite and writes an HTML report.
Execute-only --execute-only --package --module No APK, no crawl. Re-runs an already-generated suite. --test-case-id is repeatable, so a chosen few run back-to-back in one session with logout teardown between them.
Import --import-test-cases --excel-file Turns a hand-written Excel sheet into real executable test cases, resolving each described step against elements a prior crawl already captured. Fully offline — no device needed.
List apps --list-apps Lists package names that have a stored suite on disk.

Per-app, per-module isolation

Every artifact an app produces lives under its own folder, and test cases are further split by module so that one module's side effects can never contaminate another's assumptions about screen state — logging in for real during the login module must not change what the hamburger-menu suite expects to find. 

artifacts/apps/<packageName>/
├── screenshots/            crawl-time captures
├── xml-dumps/              raw UiAutomator2 hierarchy per screen
├── screen-repository/      Screen records + fingerprints
├── element-repository/     Element records + ranked locators
├── test-cases/
│   ├── hamburger-menu/  ├── login/  ├── sign-up/  └── manual/
├── navigation-graph.json
├── execution-screenshots/  labelled checkpoints + every failure
├── execution-logs/
└── reports/                generated HTML

The runtime dependency list is deliberately short: webdriverio for the Appium session, @xmldom/xmldom for hierarchy parsing, exceljs for the import path, winston for logging, dotenv for config, and app-info-parser for reading APK manifests. Gemini is reached over plain HTTP through the platform's own client — no vendor SDK.

02 Layered architecture

Clean Architecture, enforced by direction of dependency: every arrow points inward, and the domain at the centre imports nothing at all.

imports nothing

→ core
Infrastructure src/infrastructure

→ application, core
Shared src/shared
Cross-cutting primitives with no business meaning: Result<T,E>, retry with backoff, polling, path resolution, text predicates, config provider, clock and id interfaces.

Bootstrap + CLI src/bootstrap, src/interfaces
The composition root — the single place concrete classes are constructed and wired — plus argument parsing and command handling.
→ everything

Two conventions that carry most of the weight

Ports and adapters. The application layer never names a concrete class. AndroidAppiumDriver implements three separate narrow interfaces — IAppiumDriver (session lifecycle), ICaptureDriver (screenshot, page source, current package/activity) and IInteractionDriver (tap, type, clear, scroll, swipe, IME action, existence check) — so a consumer depends only on the slice it uses. Adding iOS means writing an IOSAppiumDriver against the same three interfaces; nothing is inherited.

Result<T, E>. Fallible use cases return an explicit result rather than throwing, which forces callers to handle the failure branch. Exceptions are reserved for genuinely exceptional conditions inside adapters, where they are caught and converted to typed domain errors at the boundary.

03 The pipeline

PipelineOrchestrator sequences the whole run. Each stage's output is persisted before the next begins, so any stage can be re-entered without repeating the ones before it.

  1. Device & app preparation Resolve a device (attached serial, or boot a named AVD and wait for it), validate the APK, read its manifest for package and launch activity, install and launch.
  2. Capture ScreenCaptureService takes a screenshot and a raw UiAutomator2 XML hierarchy dump, writing both to disk and returning their paths plus the current package and activity.
  3. Parse XmlElementParser walks the hierarchy into a flat list of Element records, computing a positional XPath for each node and deriving a ranked set of locator candidates.
  4. Fingerprint & deduplicate FingerprintEngine produces a stable SHA-256 signature per screen and per element. Identical screens collapse to one record; the crawler uses the signature to know whether a tap actually went anywhere.
  5. Crawl Depth-first: tap the first unvisited clickable element, re-capture, recurse or back out, bounded by --max-screens (default 100) and --max-depth (default 20). Builds a navigation graph as it goes.
  6. Generate Four generators turn stored screens and elements into test cases — menu navigation, login, sign-up, and the Excel-driven manual importer. Generation is entirely offline and deterministic; it reads the repositories, never the device.
  7. Execute TestExecutionEngine opens one session per module, runs each case's steps through TestStepExecutor, and tears down with logout between cases.
  8. Report ReportGenerator renders an HTML report: per-step status, timings, captions, embedded screenshots for labelled checkpoints and for every failure.

Two timing behaviours in the crawler are worth calling out because they were both discovered against real hardware rather than reasoned about up front. A fixed 500 ms settle before every post-tap capture stops the crawler recording a drawer mid-slide-in — without it, an entire generated menu suite once described the screen underneath the drawer. And because a WebView page load is far slower and less predictable than a native animation, the sign-up form instead re-captures until its signature stops changing between two consecutive attempts, up to five tries.

04 Locator model

Every parsed element carries a ranked list of locator candidates, not a single locator. The crawler tries them in priority order and stops at the first that works, which is what lets it keep moving on screens where the accessibility tree is transiently inconsistent.

PriorityStrategyResolves toNotes
1resource-idAppium id: Strongest for native views. Cannot resolve a bare WebView id — see §7.
2accessibility-idaccessibility id: From content-desc.
3xpath-textraw XPath Matches on visible text. Also the escape hatch for arbitrary XPath.
4xpath-class-indexraw XPath Positional path built during the walk — structural, brittle by nature.
5coordinatesmobile: clickGesture Bounds-centre tap. Bypasses the accessibility tree entirely.
—android-uiautomatorandroid= Authored, never auto-derived. Exists for UiScrollable.scrollIntoView.

Why android-uiautomator exists

Reaching an item in a virtualized list cannot be done reliably with "swipe N times, then assert" — fling momentum varies per gesture, and a swipe count calibrated on an emulator lands a row short or long on a physical device. A UiScrollable expression instead keeps swiping until the target actually materializes, evaluated on-device.

Two traps this strategy carries

scrollIntoView returns the scrollable container, not the row it found. An existence check against that expression therefore always reports true, and calling .click() on it taps the middle of the list. Scroll with the expression, then click the row by its own locator.

scrollIntoView(text("X")) matches any node with that text anywhere on screen and stops immediately. When a balance panel began rendering the text "Betway Rewards", the search matched it in 1.8 s without scrolling at all and the drawer row was never reached. Scoping the selector to resourceId(navTitle).text(label) makes the identical call scroll properly.

The nine step actions are click, type, clear, scroll, swipe, press_ime_action, back, wait, plus the two assertions verify_text and verify_element_exists. Three of them — swipe, clear and press_ime_action — were added because a WebView surface demanded them; §7 explains each.

05 Execution engine

Credentials resolve per device, at execution time

Generated test cases contain {{account.mobileNumber}} and {{account.password}} placeholders, never literal secrets. Before a session opens, TestExecutionEngine looks up the account bound to the device serial and substitutes them. Two consequences follow: stored test-case JSON holds no password, and two devices can run the same case concurrently as different accounts. 

config/test-accounts.json   (gitignored)
{
  "accounts":       { "s21-primary": {...}, "s22-secondary": {...} },
  "deviceAccounts": { "<deviceA-serial>": "s21-primary",
                      "<deviceB-serial>": "s22-secondary" }
}

An unresolved placeholder is a hard failure before the session opens — never a value passed through. Typing a literal {{account.password}} into a real login form repeatedly locks the account, which is not a hypothetical: it has already happened once on this project's second test account.

The step fallback ladder

TestStepExecutor.execute() is where resilience lives. A failing step is not immediately a failing test:

  1. Perform Dispatch the action. On success, capture a screenshot if the step is labelled, and pass.
  2. Optional? Pass as skipped A step marked optional that fails becomes a no-op pass — for conditional things like a popup that does not appear every run. It bypasses the rungs below entirely.
  3. Dismiss an overlay, then retry once Look for a close/dismiss/skip control, tap it, re-capture and check the result is not a real-money screen, then retry the original step.
  4. Heal the locator, then retry once Re-parse the current screen and fingerprint-match the stored element against every candidate (§6). On a confident match, update the repository and retry.
  5. Fail with evidence Capture a screenshot regardless of labelling, record the reason and stack trace, and stop the case.

Screenshots are captured only for labelled steps plus any failed step. Capturing every step produced ~146 images for a single 13-item menu tour, burying the handful that actually evidenced anything; the label doubles as the report caption.

06 Self-healing

When a stored locator stops resolving, LocatorHealingEngine re-parses the live screen and scores the stored element's fingerprint against every fresh candidate. The comparison is deterministic and weighted — no model involved:

ComponentWeightComponentWeight
className0.25bounds0.10
resourceId0.20parentClassName0.05
accessibilityId0.15childClassNames0.05
text0.15clickable0.05

Class name and resource id dominate because they are the most stable identifiers; bounds contribute least because they shift across screen sizes. Above a 0.6 confidence threshold, the element repository is updated so the healed locator persists into future runs rather than being rediscovered every time.

Gemini is consulted only if an AI fallback is injected and deterministic matching found nothing confident enough. The AI layer sits behind IAiLocatorHealingFallback and IAiScreenAnalyzer, with rate limiting, timeout, retry-with-backoff, and strict response validation in front of it. With no API key configured the platform runs fully deterministically.

Healing refuses to run at all on a screen that looks like a real-money flow — see §9.

07 How WebView is handled

The target app renders everything below its native toolbar inside a WebView. This section is the accumulated result of getting that to work reliably on physical devices — every item below was diagnosed live, not anticipated.

The core decision: no context switching

Appium offers a hybrid-app model where you call getContexts(), switch from NATIVE_APP to WEBVIEW_<package>, and then drive the page with ordinary Selenium CSS selectors through ChromeDriver. This platform never does that. It stays in the native context permanently and drives WebView content through UiAutomator2's accessibility tree — the same tree, the same locators, and the same driver methods it uses for native widgets.

Native view hierarchy WebView content, reached through that same hierarchy

Three reasons that choice holds up here:

  • Version coupling. Context switching requires a ChromeDriver binary matching the device's WebView version. Across a mixed fleet of physical devices that becomes a per-device provisioning problem before a single test runs.
  • Mixed screens. Real screens interleave the two — a native toolbar and drawer wrapped around WebView content, with popups from both worlds stacking on top of each other. A test that has to switch context mid-flow to tap a native toolbar button, switch back for the page, and switch again for a native dialog is far more fragile than one that never switches at all.
  • It works. WebView nodes surface in the accessibility tree as android.widget.TextView, android.widget.EditText and friends, carrying their web id attributes through as resource-id. That is enough to locate and act on them.

The cost is that WebView elements behave subtly differently from native ones through that interface. Each difference below is handled explicitly.

Trap 1 — bare WebView ids are unreachable via resource-id

A native Android view id arrives fully qualified: com.betwayafrica.za:id/toolbarDeposit. A WebView id arrives bare: transaction-history-search-btn, with no package part at all. The resource-id strategy maps to Appium's id locator, which prefixes a bare id with the app package — so it silently searches for com.betwayafrica.za:id/transaction-history-search-btn, which does not exist. 

// Never resolves — the id strategy package-prefixes it.
{ strategy: 'resource-id', value: 'transaction-history-search-btn' }

// Resolves. XPath matches the attribute literally.
const WEB_ID = (id) => ({
  strategy: 'xpath-text',
  value: `//*[@resource-id="${id}"]`,
});
Why this one mattered most

The failure is silent in exactly the wrong place. Every popup-dismissal step in every generated suite targeted modal-close-btn — a bare WebView id — and was marked optional. So each one failed to resolve, was treated as "the popup isn't there", and passed. The suites had been walking straight past real popups for weeks while reporting green. Fixing the locator immediately made the reset script start dismissing two stacked popup layers it had never touched.

Trap 2 — WebView text nodes report clickable="false"

Tab labels and rows inside the WebView carry no resource-id and advertise clickable="false", so a naive "only tap clickable elements" filter skips them entirely. A tap at their coordinates is nonetheless routed to the WebView and handled correctly. They are targeted by exact text: 

const WEB_TEXT = (text) => ({
  strategy: 'xpath-text',
  value: `//android.widget.TextView[@text="${text}"]`,
});

Text matching demands care about uniqueness. "Deposits" and "Withdrawals" also appear on the toolbar and bottom navigation, so the filter tabs are targeted by their stable WebView ids instead. Where an id is unavailable, the selector is scoped to the container that makes it unique — drawer rows match on resourceId(navTitle) and text, because several drawer labels are duplicated elsewhere on screen.

Trap 3 — setValue rejected with ACTION_SET_PROGRESS

setValue asks the accessibility layer to set an element's text. A WebView-hosted input can advertise the wrong action for that: the transaction-history search box reports ACTION_SET_PROGRESS, as though it were a slider, and rejects the call — while accepting ordinary keystrokes perfectly well. sendKeys catches the rejection and falls back to focus-then-type: 

try {
  await element.setValue(value);
} catch (setValueError) {
  // Focus it and type instead — same route as the coordinate branch,
  // but still located via the accessibility tree, so the step stays
  // portable across devices and screen sizes.
  await element.click();
  await handle.executeScript('mobile: type', { text: value });
}

Trap 4 — the search box ignores keystrokes until the IME action fires

Typing into that same box filters nothing. The page listens for the keyboard's Search/Go key, not for input events. This required a new framework action, press_ime_action, carrying the action name in step.value and defaulting to "search": 

await handle.executeScript('mobile: performEditorAction', { action });
Do not reach for hideKeyboard

Appium's hideKeyboard presses Back on Android. On a WebView screen that navigates out of the page entirely — it blanked Transaction History mid-test. The same rule applies to closing popups: always tap the app's own close control, never Back, which reaches the app root and raises an "Exit?" confirmation.

Trap 5 — clearing needs its own action

Typing an empty string is a no-op, so resetting a search box between queries could not be expressed at all. clear was added as a distinct action calling clearValue(), which meant threading it through the driver interface, the WebdriverIO session handle and its adapter. The test then hard-asserts the result with a verify_text against the placeholder, rather than trusting the clear silently worked.

Trap 6 — the accessibility tree walk hangs on nested WebViews

UiAutomator2's default tree walk can stall for 10 s+ per command, eventually never recovering, on screens with deeply nested or overlapping WebViews — a popup opened on top of another popup. One capability setting resolves it, applied to every session: 

'appium:settings[enforceXPath1]': true,
'appium:adbExecTimeout': 60_000,  // 20s default is too tight under real load
'appium:noReset': true,

Trap 7 — WebView page loads outrun the capture

A native transition settles well under a second. A WebView-hosted form can still be mid-navigation, loading over the previous screen, long after the tap that opened it returned — an immediate capture caught the old login screen still fading out underneath the new page. The crawler therefore treats the two differently: a flat 500 ms settle for native transitions, and for WebView forms a re-capture loop that continues until the screen signature stops changing between consecutive attempts.

The same asymmetry shows up in assertions. verify_element_exists is an instantaneous check with no implicit wait, and on a congested network a sign-in has been observed still spinning ten seconds after submit — so post-login assertions are written as retry loops with real slack rather than a single optimistic check.

Trap 8 — WebView markup produces overlapping duplicate fields

The sign-up form's "Mobile Number" row renders as two overlapping EditText nodes 27 px apart — one with a resource id, one without — where genuinely distinct rows sit 130 px+ apart. The generator collapses any two fields whose vertical centres fall within 60 px into a single logical field, so it does not emit two typing steps for one input.

Trap 9 — several scrollable containers, one of them 2px tall

The drawer screen exposes three scrollable containers: the drawer list, a top-navigation GridView, and a 2 px-tall WebView strip. An unscoped new UiSelector().scrollable(true) picks whichever the tree yields first, which may scroll nothing at all. Every scroll expression names its container explicitly: 

new UiScrollable(new UiSelector().resourceId("…:id/leftNavigationItems"))
  .setMaxSearchSwipes(12)
  .scrollIntoView(new UiSelector().resourceId("…:id/navTitle").text("Log Out"))

Trap 10 — back() only partially closes a WebView popup

During crawling, a single back press left a WebView sign-up popup open. The crawler then tapped the home screen's cached Login button on top of it, stacking a second popup and hanging the accessibility service. Every dismissal is now re-verified by re-capturing and comparing the screen signature, retrying up to three times, rather than assuming one recognized close tap was enough.

The coordinate escape hatch

Underneath all of this sits the last-resort strategy. A WebView-hosted field's resource id can be an ephemeral id the accessibility tree assigns fresh per page load rather than a stable Android view id, so tree-based lookup can fail even though the field is visibly present. The coordinates locator taps its captured bounds centre via mobile: clickGesture and then types into whatever has focus — no element lookup involved. It is deliberately last: it survives a flaky tree but not a moved element.

08 Parallel execution

Playwright parallelizes by opening many cheap isolated browser contexts in one process. A phone has one foreground app and one screen, so there is no equivalent — the device is the unit of parallelism, and tools/run-parallel.js runs one worker per device.

Each worker needs three things of its own, and all three are failure modes if shared:

ResourceMechanismIf shared
Appium server portAPPIUM_PORT, from 4723 Sessions collide on one server.
UiAutomator2 systemPortAPPIUM_SYSTEMPORT, from 8200 The second worker fails to bind and tears down the bridge the first is already using.
Test accountdeviceAccounts map Workers log each other out mid-suite.
The env-var naming trap

EnvConfigProvider maps a dot-path config key to an env var by upper-casing and removing the dots — so appium.systemPort becomes APPIUM_SYSTEMPORT, not APPIUM_SYSTEM_PORT. Setting the plausible-looking name silently does nothing: both workers took 8200, and the first run of the parallel runner failed on both devices at once. Values also arrive as strings and need an explicit Number() before reaching the capability.

Devices are verified present over adb and every account assignment is checked before anything launches, so a misconfigured run fails in seconds rather than mid-suite. Device resets run sequentially even though the suites run concurrently — the reset script hardcodes port 4723 and sets no systemPort, so concurrent resets would collide on 8200. 

node tools/run-parallel.js --package com.betwayafrica.za --module manual \
  --run <deviceA-serial>=<hamburger-tour-id> \
  --run <deviceB-serial>=<my-bets-id>,<transaction-history-id>

Measured on the most recent two-device run: 547 s wall clock against roughly 725 s sequential. The speedup is bounded by the slowest single device, not by total work — the hamburger tour alone accounts for the full 547 s.

09 Safety model

The platform drives a real betting app signed in to real accounts holding real balances. Several mechanisms exist purely to constrain what it can do.

Real-money screens are refused, not navigated

isSensitiveFinancialElement recognizes deposit, withdrawal, voucher and payment surfaces. Two independent paths check it. Overlay dismissal re-captures after its tap and backs out if it landed somewhere sensitive; locator healing refuses every strategy — coordinate self-heal, fingerprint match and AI fallback alike — the instant it detects one. The safe response is always to fail the step rather than guess at an interaction.

Why both guards exist

An overlay-dismissal tap once landed on an unrelated element that cascaded into a Deposit Funds screen. The very next assertion passed anyway, because it targeted a header present on almost every screen — masking the drift until a later coordinate-healing fallback typed a cached password into a Voucher Pin field. Checking after the dismissal catches the drift at its source; refusing to heal catches it if anything still gets through.

Standing constraints

  • Real credentials never enter version control. config/test-accounts.json is gitignored; the committed example holds placeholders only. The Gemini key lives only in .env.
  • Generated test cases and run artifacts are gitignored — they show balances and bet history.
  • Test cases never type into or submit real-money fields. Deposit, Withdraw, Change Password, Update Details, Promo Voucher and Responsible Gaming screens are opened and screenshotted only.
  • The biometric enrolment prompt is always Skipped, never Allowed, on a real account.
  • Never use Back to close a popup or screen — tap the app's own close control.
  • Logs are redacted; resolved credentials are never printed, and credential errors never include the resolved value.

One deliberate exception: the overlay-recovery path still falls back to back() when it finds no recognizable close control on a suspected real-money screen, capped at a fixed number of escapes per run. Getting off that screen outweighs the general rule, and the cap stops it wandering.
